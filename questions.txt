dist-newstyle/ isn't ignored. should it be ? any other built binaries tht aren't? comprehensively review .gitignore and .dockerignore and ensure it's aligned with the new repo layout

  A. dist-newstyle/ IS ignored -- .gitignore:33, and .dockerignore:37-38 as `**/dist-newstyle`.
     `git check-ignore dist-newstyle/x` returns IGNORED. The rule is unanchored on purpose:
     cabal rejects `builddir` in project/config files and ignores CABAL_BUILDDIR, so a bare
     `cabal build` writes a root wherever it is run, and only a class rule catches all of them.

     No tracked file is a build product. `git ls-files` matching
     *.o|hi|so|dylib|a|exe|jar|class|whl|pyc or dist-newstyle|node_modules|/output/ returns
     nothing. Both contracts already cover: .build/ .data/ .test_data/ gen/ dist-newstyle/
     .cabal-sandbox/ .ghc.environment.* *.o *.hi *.dyn_o *.dyn_hi *.hie *.tla *.cfg
     node_modules/ ui/.spago ui/output ui/dist __pycache__ *.py[cod] .pytest_cache .coverage
     htmlcov playwright-report test-results *.log *.pid *.sock *.lock *.freeze package-lock.json
     npm-shrinkwrap.json pnpm-lock.yaml go.sum test-secrets.dhall.

     Three genuine gaps, all currently NOT-IGNORED by either contract:
       1. cabal.project.local -- cabal writes it on `cabal configure`. Pure resolver output.
       2. .DS_Store -- Finder writes it on every apple substrate, which is a catalog member.
       3. pb/.venv/ -- Poetry's in-project virtualenv. Phase 3 creates it; without a rule the
          first `poetry install` puts a dependency tree into the source snapshot.
     I am adding all three as part of Phase 3, to both contracts.

     Two candidates I am deliberately NOT adding: .stack-work/ and .direnv/ | result. The
     .gitignore preamble makes a rule a claim that the target tree contains the path, and
     artifact_policy rule r15 fails a rule for a path the tree does not have. amoebius uses
     neither stack nor nix, so those rules would be exactly the "second home for a generated
     class" the preamble forbids.

     Alignment with the new layout is otherwise clean. The four migration rules (/gen/,
     /DEVELOPMENT_PLAN/evidence/, /test/enumeration/, /test/golden/phase_*_ledger.json) are
     the section 2.2 surfaces and retire with their roots; none of those directories exists
     today, so they are already dead rules awaiting their closure phase.


Why so many Dockerfiles, and not all built from ubuntu ? I was expecting only one, with every service contained (vault, pulsar, mino, prometheus, grafana, redis, playwright, etc). this should be a generalized version of the Dockerfile doctrine in ~/hostbootstrap.

  A. There is already exactly one, and it is already the monocontainer you describe. The
     premise is out of date. `git ls-files | grep -i dockerfile` returns four paths and only
     one of them is a recipe:
       src/Amoebius/Image/RenderDockerfile.hs           the renderer (not a Dockerfile)
       test/fixture/base_image_registry/Dockerfile.golden          the rendered recipe, sealed
       test/fixture/base_image_registry/haskell_arm64.Dockerfile   a test fixture
       test/mutant/base_image_registry/dockerfile-handedit.mutant  a seeded mutant
     The last two exist to be checked, not to be built from; the mutant's whole content is a
     hand-edit the gate must catch.

     The one recipe is `FROM ubuntu:24.04@sha256:561618e2...` and it is a total projection of
     dhall/amoebius/BakeCatalog.dhall, not hand-written -- its second line is the
     GENERATED BY ... DO NOT EDIT stamp. It already contains the service set you name:
     docker-registry, redis-server, redis-tools, postgresql-16, patroni, openjdk-21-jre,
     ca-certificates, curl, unzip, g++ via pinned apt versions, then minio, vault, prometheus
     and the rest as publisher artifacts, each fetched with the publisher's own checksum
     manifest verified in the same layer. It ends USER 65532:65532,
     ENTRYPOINT ["/usr/bin/amoebius"].

     So it is already the generalized form of ~/hostbootstrap/docker/basecontainer.Dockerfile,
     with one addition hostbootstrap does not have: the recipe is data (a typed Dhall catalog)
     rather than text, so a service is added by a catalog row and the bytes are re-derived.
     Phase 5 is the phase that seals this -- it moves the digest out of the tracked bytes
     (ARG BASE_IMAGE / FROM ${BASE_IMAGE}) so a republished upstream base does not produce a
     diff nobody decided.


src/Infernix exists but no /jitML why ? review ~/infernix and ~/jitML and propose combined structure. consider general shape for amoebius extensions, if that concept even makes sense, and how we want to represent these highly generalized ML workflows

  A. Both are present; they are named inconsistently, and that is the actual defect.
     amoebius.cabal declares four libraries for them:
       library infernix     (1652) exposes Infernix.Adapter.{Core,Store,Pulsar,Secrets,Engine}
                                   and Infernix.Inference.Deterministic  -> src/Infernix/**
       library infernix-ui  (1684) exposes Amoebius.Infernix.UiAdapter   -> src/Amoebius/**
       library jitml        (1705) exposes Amoebius.JitML.CudaArtifactLift
       library jitml-ui     (1736) exposes Amoebius.JitML.UiAdapter
     So the infernix core adapter squats the upstream `Infernix.*` namespace at src/Infernix/,
     while every other adapter -- including infernix's own UI half -- lives under
     `Amoebius.*`. There is no design reason for the split; src/Infernix should be
     src/Amoebius/Infernix/Adapter/** so the rule is "amoebius code is Amoebius.*, full stop."
     That also removes a real hazard: `library infernix` build-depends on the upstream package
     `infernix` AND exposes modules in that package's own namespace, so the two can shadow.

     Neither core lives here. cabal.project pulls both as source-repository-package release
     channels (github.com/Tuee22/infernix, github.com/Tuee22/jitML, tag master). They used to
     be reached by `hs-source-dirs: ../../infernix/src`, which resolved against your home
     directory rather than the source snapshot; Phase 1 replaced that.

     Proposed combined structure -- the "extension" shape does make sense, and the repository
     already has the seam for it. documents/engineering/lift_and_compose_doctrine.md and
     capability_extension_doctrine.md define it: an external ML project is not imported, it is
     LIFTED behind a typed port. Every such project then needs exactly three things and no
     more:
       1. a core adapter          Amoebius.<Name>.Adapter.*   -- typed port over the upstream
       2. a UI adapter            Amoebius.<Name>.UiAdapter   -- projection into the UI plan
       3. a capability entry      a row in the Dhall capability union
     infernix and jitML both already have (1) and (2). Making the namespace uniform turns that
     accidental pair into a stated pattern, which is what lets a third ML project be added
     without inventing a fourth layout. The general workflow representation is the DSL's own:
     an ML workflow is a Dhall value that names a capability and its artifacts, and the
     adapters turn it into content-addressed artifacts plus Pulsar work -- not a new runtime.

     One live defect found while checking this, already recorded against Phase 65:
     `library jitml` documents that JitML.Codegen.RuntimeOperationsCuda was on its surface but
     exists in neither this repository nor the resolved jitml package.


why so much python ? tools/ and elsewhere. in a haskell project should we have any .py outside of pb/ ?

  A. 172 of the 209 tracked files in tools/ are Python; test/ has 8 more; pb/ has 5. So the
     honest count is 180 .py files outside pb/, against 303 .hs files in src/.

     There is no doctrine section that justifies this, and it does sit uneasily with the rule
     the layout doctrine itself states (repository_layout_doctrine.md:164): roots are named by
     their reader -- "dhall/ is read by the Dhall interpreter, proto/ by protoc, pb/ by
     CPython, ui/ by purs, pulumi/ by the Pulumi engine, and src/ | app/ by GHC." By that rule
     tools/ is a second CPython root that the sentence does not admit, and pb/ is described as
     THE Python distribution.

     The defensible core is small. A phase gate must run before the thing it gates exists and
     must keep running when the Haskell does not compile -- that is why pb/ is Python at all
     (substrate_doctrine.md section 6), and a gate that shells out to cabal has the same
     property. tools/gate_common.py, artifact_policy.py, attestation.py, containment.py,
     ledger_lint.py, doc_lint.py, host_platform.py and mutant_registry.py are that core: about
     3,200 lines that decide policy over the repository as text, before and independently of
     the compiler.

     The indefensible part is the other ~160 files. tools/*_live.py in particular are cluster
     drivers -- they talk to kind, Vault, Pulsar, MinIO and Kubernetes. That is exactly the
     work the no-PATH, absolute-path, typed-argv Haskell host layer exists to do, reimplemented
     in an untyped language with none of those guarantees, and with no type checker, formatter,
     linter or test suite configured for it anywhere in the repository. It is also where the
     duplication already bit: tools/toolchain.py and pb/pb/bootstrap_toolchain.py each
     implemented the version algebra, and they disagreed on platform normalization until
     Phase 1 made tools/host_platform.py the one normalizer.

     My answer to the question as asked: yes, .py outside pb/ is justified, but only for the
     policy-over-text gate kernel, which should be a named, quality-gated set on the same
     terms Phase 3 is about to impose on pb/ -- black, ruff, mypy strict, no Any, tests. Every
     *_live.py that drives a cluster should migrate into the Haskell host layer as its owning
     phase reopens. I have not opened that migration; it is not phases 3-5's to open, and it
     needs a row in legacy_tracking_for_deletion.md with an owning phase before anyone starts.


proto/ -- what are we using proto for ? we should be using CBOR for all serialization so what do we need proto for ?

  A. Both are correct and they are not the same layer. proto/ holds exactly one file,
     proto/Amoebius/Pulsar/Proto/PulsarApi.proto, and it is Apache Pulsar's OWN wire format --
     not amoebius's choice and not amoebius's to change.

     pulsar_client_doctrine.md section 3.1 draws the line explicitly: "The command/metadata
     layer is protobuf -- that is Pulsar's own wire format (BaseCommand, message metadata, via
     proto-lens), and it is not amoebius's to change. The application payload -- the raw
     payload tail after the metadata -- is amoebius's, and it is exclusively CBOR. There is no
     JSON, no base64, no protobuf, and no untyped ByteString application payload: a Pulsar
     message body that is not CBOR is unrepresentable."

     A Pulsar frame is totalSize | commandSize | command(protobuf) [| magic+crc32c |
     metadataSize | metadata(protobuf) | payload]. To speak the protocol at all you must
     decode BaseCommand. Every byte amoebius itself authors -- the payload tail -- is CBOR via
     serialise/cborg, canonically encoded wherever it is content-addressed, and the illegal
     state is catalogued (illegal_state_capability_messaging.md 3.23, "a non-CBOR Pulsar
     payload").

     So: keep proto/. It is a vendored third-party schema, and the bindings it generates are
     build artifacts under .build/proto/ -- never committed. Removing it would mean writing
     Pulsar's protocol by hand, which the doctrine also forbids ("Hand-rolled wire parsing of
     the protobuf bodies is" not admitted).


pulumi/ -- why one random .yaml file ?

  A. It is one file -- pulumi/child-cluster/Pulumi.yaml -- and it is not random, but the root
     is currently doing very little for its size.

     The file is a Pulumi YAML-runtime program: stack identity for a child cluster, two config
     inputs (childId, parentCluster), four outputs including checkpointCustody:
     vault-enveloped-minio, and one command:local:Command resource whose create/delete shell
     out to kind by absolute path (/phase42/bin/kind ...). Its description names it the
     "Phase-42 child-cluster stack identity and encrypted-checkpoint owner" -- a pre-re-baseline
     ordinal, so it belongs to what is now Phase 56 (hostless provider child + convergence).

     The root exists for the reader rule again: pulumi/ is "authored programs the Pulumi engine
     executes verbatim" (repository_layout_doctrine.md:88). The engine reads Pulumi.yaml itself,
     so it cannot live in src/. The Haskell that decides WHAT to ask Pulumi does live in src/ --
     src/Amoebius/Pulumi/** and src/Amoebius/Capacity/PulumiExecution.hs.

     Two real observations. First, the embedded /phase42/ paths are a phase ordinal inside an
     authored file, which is what Phase 2's de-phased-naming rule exists to catch -- it is not
     caught today because the ordinal is inside the file body rather than in its name. Second,
     one YAML file is a thin justification for a top-level root; if the provider phases end up
     needing nothing more than stack identity, this should become a rendered artifact under
     .build/ like every other manifest amoebius generates, and the root retires. That is a
     Phase 55/56 decision, not a layout decision, so I have left it alone.


what is the deal with the vendor/ folder ? why do we need dual ? why is this root level instead of somewhere in src/ ?

  A. vendor/dual is a reviewed copy of github.com/strake/dual.hs (dual-0.1.1.2), four files,
     with vendor/dual/PROVENANCE.md recording why.

     Why we need it: it is a transitive dependency of supernova, the Pulsar library
     cabal.project pulls as a source-repository-package. Nothing in src/ imports
     Control.Category.Dual or Data.Bifunctor.Flip directly -- I checked. GHC 9.12 began
     checking the unary superclasses of Eq2/Ord2/Read2/Show2; the released dual supplies the
     binary instances but not Eq1/Ord1/Read1/Show1, so it fails to compile. The vendored copy
     adds those four instances using the same argument reversal the binary instances already
     use, and changes nothing else.

     Why vendored rather than patched: dual is two small modules and the edit changes one
     module's instance set. A patch would have to be re-reviewed against whatever the upstream
     branch head happened to be on each clean resolution -- which is precisely the frozen-revision
     coupling this repository is removing. supernova takes the opposite trade for the opposite
     reason and stays a four-line patch in patches/supernova_ghc_9_12.patch.

     Why root level and not in src/: because src/** is defined as "authored Haskell library
     source; one module tree, read by GHC" and this source is not authored here. Putting it in
     src/ would make foreign source indistinguishable from ours in the one tree the whole
     project reads, and it would have to join the single amoebius.cabal package. Instead it is
     one of exactly two units section 2.1 admits apart, on the ground of foreign provenance
     (the other is probe/, on foreign resolution). cabal.project lists all three packages and
     says so in its own comment.

     Standing cost to accept: no automatic pickup of upstream dual fixes. Intended -- the
     package has had no release in the compatibility window.


~/infernix and ~/jitML both have sophisticated ways of ensuring we can't represent using more resources (cpu/ram/storage/vram etc) than what is available and that each process has a known resource footprint that it doesn't exceed. are we doing something similar here ?

  A. Yes, and by volume amoebius's version is the larger of the two -- but it is weaker in
     exactly the dimension infernix is strongest.

     What is here: seven doctrine documents (resource_capacity_{doctrine,types,schema,folds,
     construction,sources,storage}.md), 19 modules under src/Amoebius/Capacity/** and 7 under
     src/Amoebius/Scheduler/**. Capacity/Types.hs carries Demand, AvailableCapacity and
     Headroom as distinct newtypes over one ResourceVector with an explicit Axis, a smart
     constructor mkResourceEnvelope :: ... -> Either PlacementError ResourceEnvelope that
     refuses a requests/limits/padding triple that does not cohere, an Overcommit policy with
     CpuOvercommitPolicy, GrowthQuota, and a PlacementError sum. Phases 14-19 are five sealed
     phases of pure folds over exactly this. Capacity/Etcd.hs models WAL overshoot,
     preallocation, snapshot temporaries and defrag copy; NodeLocalStorage.hs models the
     nodefs/imagefs split. There is also a live pre-binary version:
     pb/bootstrap_execution_envelope.json plus validate_envelope() computes an ORDERED PEAK
     disk requirement across install steps and refuses installer-cpu-overdraw /
     -memory-overdraw / -disk-overdraw before any mutation, behind a one-shot
     ValidatedExecution token that also refuses host-fingerprint-changed.

     Where infernix is ahead: type-level foreclosure proved by compile failure.
     ~/infernix/test/compile-fail/fail/ has 92 cases -- CannotConstructMemoryGrant,
     CannotReadMemoryCeiling, CannotCoerceMemoryGrantResource, PodEnforcerVramGrant,
     VramEnforcerHostGrant, CompiledPlacementHasNoResources -- i.e. it proves you cannot even
     WRITE the program that spends a grant from the wrong enforcer domain. amoebius's
     test/negative/compile_fail/ has three directories, none of them about capacity. amoebius
     forecloses at the smart constructor and in the illegal-state catalog (99 entries, 14
     capacity/resource-related), which is a runtime Either rather than a compile error.

     So the honest answer: the model is at least as rich and much better documented; the
     enforcement is one notch weaker. Closing the gap means adding capacity compile-fail
     negatives -- the machinery already exists (tools/compile_fail.py, test/negative/compile_fail/)
     and infernix's own case list is the obvious source for what to prove. I have not added
     them; that belongs to whichever phase reopens the capacity folds, not to phases 3-5.


why is there a ui/ folder ? shouldn't all frontend code be generated by .hs ? i would prefer a jit-like behaviour for the Ui server (using spago)

  A. It is 13 files and none of them is per-app frontend code. ui/ holds the ONE fixed generic
     PureScript interpreter: Main.purs, Amoebius/Ui/Components.purs, Amoebius/Ui/Interpreter.purs,
     and seven Amoebius/Ui/Offline/* modules (ServiceWorker, Leader, Replay, BlobStore,
     Partition, Migration, Store, Crypto), plus ui/spago.yaml.

     That IS the design you are describing, stated in low_code_ui_runtime_doctrine.md section 1:
     "Generating a bespoke frontend ... " is rejected; instead one checked Dhall value is
     projected into two runtime plans -- "a client plan for a generic PureScript interpreter
     and a server plan" -- and "PureScript owns the fixed browser interpreter." An app's UI is
     data (a Dhall value compiled through a Haskell IR into a plan), and the plan is
     interpreted by this one bundle. Adding a UI adds no PureScript. Section 4.4's rule that
     external links are names resolved by a trusted catalog is the same idea: the interpreter
     is fixed and everything app-specific is a value it reads.

     So the folder is not generated because it is the interpreter, and an interpreter cannot be
     generated by the thing it interprets. What IS generated and never committed is the bundle:
     the doctrine's generated-file row reads "Per-app plans/content manifests and the generic
     runtime's catalog codecs/bundle are generated and never committed." Both ignore contracts
     already exclude ui/.spago, ui/output and ui/dist.

     On jit-like behaviour with spago: that is already the intended shape -- spago is a
     resolved tool (tools/toolchain_requirements.json lists purs and spago) and the bundle is a
     build artifact produced on demand, not a checked-in asset. What does not exist yet is the
     cache that makes it jit rather than rebuild-every-time; that is Phase 59's
     determinism/jit-cache work, and it is blocked behind the current chain.
